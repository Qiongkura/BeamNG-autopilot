## 1. 实测到的三个真实缺陷（按优先级）

### 1.1 已修：障碍风险层把路侧物体当碰撞 → 车被永久按死

首次基线 151 帧中 144 帧 `minimal_risk / obstacle contact risk`、油门 0 刹车 1，
而 `fwd_clear` 中位 16.4 m。根因是接触带判定排在横向走廊过滤之前。已修（`511beca`）：
走廊门控提前 + 走廊侵入预测在 3 s 窗口按 0.5 s 采样。修后同场景 14.4 m → 89.5 m。

### 1.2 待修（最高优先级）：碰撞发生在"感知看不到边界 + 车已在铺装面外"时

`collision_count=1`（`damage 0 → 68.8`，t=34.34 s）。撞车前后逐帧（`damage_town_check.json`）：

```
t=32.24 v=0.09 safe  steer=+0.55 edge_over=3.925 paired=1 fwd=1.69
t=33.00 v=1.54 safe  steer=+0.55 edge_over=3.847 paired=1 fwd=1.18
t=33.70 v=2.78 minimal_risk  obstacle contact risk  brk=1.00 fwd=-0.44
t=34.34 v=2.66 safe  brk=0.60 edge_over=2.323 paired=0 fwd=19.01   <- 损伤出现
```

两个可操作的问题：

1. **`fwd_clear` 不可信**：同几帧 1.18 → **−0.44**（负值）→ 19.0 → **−0.22** → 16.9。
   负值与 1 帧内 17 m 的跳变都不合理；紧急刹车层（`emergency_speed_limit_mps`）与
   `force_stop` 直接吃这个值，所以它一跳变，风险判定就跟着翻转（33.70 停、34.34 放行）。
   入口：`beamng_autopilot/perception.py::forward_clearance_m`（近场地面剔除、走廊宽度、
   射线命中过滤）。
2. **感知无边界时不设防**：撞击时刻 `lat_left/lat_right=None`、`lane_paired=0`，
   但 `edge_over=2.3 m`（车已越过道路自身边缘 2.3 m）却只进遥测、不进控制。
   `_perception_off_road_m` 在没有边界时返回 0（"盲"），所以 `off_recover` 不触发；
   方案与 AGENTS.md 允许的合法降级是**fail-closed 停车**，前提是判据来自感知。
   可用判据：语义 `drivable` 掩码对**车身自身投影**的覆盖率（这是感知，不是地图），
   连续 N 帧低于阈值即刹停。
   入口：`fsd_drive._perception_off_road_m`（当前只认边界）、`Scene.grid.drivable`。

### 1.3 已定位（数据，不再是推测）：`stale sensor` = tick 预算把 range/object 饿死

补完遥测后又跑了一次实车（`logs/fsd_benchmark/direct_errdiag.json`，40 s / 49 帧），
把新增的 `errors` / `head_errors` / `head_worker` / `range_worker` 四列与**既有的**
`budget_skips` / `tick_ms` 一起对照了五次跑次：

| 跑次 | 帧 | 有 budget skip 的帧 | `range_s` p50 | object age >2 s | `tick_ms.ring` p50 | `tick_ms.total` p50 |
| --- | --- | --- | --- | --- | --- | --- |
| `town_1789878295`（基线） | 151 | **151（100%）** | **61.9 s** | 145/151 | 546 ms | 601 ms |
| `town_1789878735`（E1） | 120 | **120（100%）** | **61.7 s** | 116/120 | 672 ms | 759 ms |
| `direct_town_baseline` | 47 | 44（94%） | 9.1 s | 40/47 | 507 ms | 625 ms |
| `damage_town_check` | 52 | 7（13%） | 0.01 s | 0/52 | 376 ms | 643 ms |
| `direct_errdiag`（本次） | 49 | 5（10%） | 0.01 s | 0/49 | 387 ms | 686 ms |

**结论：**

1. **没有任何异常。** 新加的 `errors` / `head_errors` 在这 49 帧里**全是 `null`**——
   ring / range / object / bev_fusion / tracker 一次都没抛。LiDAR 与 YOLO 停摆**不是崩溃、
   也不是模型报错**，那条"看它们抛什么"的假设被数据否掉了。
2. **停摆 = tick 预算调速器把 `range` 与 `object` 永久延后**：`budget_skips` 里
   `range` 出现在 151/151、120/120 帧，`object` 出现在 147/151、117/120 帧。
3. **触发条件是「整帧累计耗时 > 0.45 s」，而 ring 一步就吃掉 376–672 ms。**
   `_budget_defers`（`fsd_stack`）判的是 `elapsed = time.time() - _tick_cost0`，
   **不是这个模态自己的开销**；ring 一旦超支，后面每一步的延后判定就无条件成立。
   它只对 `semantic` 有 strict 豁免，`object` / `range` 没有。
4. **所以 `range_age` 与被跳过的帧占比成正比**：100% 跳 → p50 61.9 s（≈ 跑次长度的一半，
   age 从最后一次成功扫描起线性增长），10–13% 跳 → 0.01 s。
   `range_age > STALE_RANGE_S(2.0)` 因此恒真 → 全程 `degraded`（150/151）、
   车速 p50 = **0.00 m/s**。**这同时是 §12「no_stall 十组全失败」的根因。**
5. **这是一次优先级倒置**：被牺牲的 `range` 复用时只要 15 ms、真扫描 250 ms，
   而被保下来的 ring 是它的 1.5–2.7 倍。
6. `tick_ms` 分解：ring 占 91%（546/601），`range` 15 ms、`plan` 35 ms ——
   所以 §12 里「控制周期 P95 700–1600 ms」的大头同样在 ring（相机环 + 同步跑的 head）。

诊断缺口已补上（`871f0c4` / `40b69b9`）：`errors` / `head_errors` / `head_worker` /
`range_worker` 四列已进逐帧遥测，async 路径下的 `hydra.errors`（此前**完全不可见**，
sync 路径的 head 异常也只进内存）现在也落盘。这四列在本次跑次里的价值是**否证**——
确认无异常，把问题锁定在调速器而不是感知本身。

**这一轮没有验证保活，因为保活的强制分支从未执行。** 但要说准为什么——**不是「输入
从来没到过界」**，逐帧读数（`range_sched.age_s`）显示两臂都有帧越过保活界：

| 臂 | 逐轮 `range_age` max（s） | `range_age ≥ 1.0 s` 的帧 | defer 帧 |
| --- | --- | --- | --- |
| OFF | 1.337 / 0.605 / **2.232** / 1.335 | 5 / 0 / 11 / 3 = **19** | 19 |
| ON | 1.322 / 1.276 / 1.199 / 1.231 | 1 / 3 / 1 / 2 = **7** | 7 |

两个阈值分属两个模块，**别混**：保活界是 `fsd_stack.py` 的
`RANGE_KEEPALIVE_S = 1.0` / `OBJECT_KEEPALIVE_S = 2.0`；`STALE_RANGE_S = 2.0` 在
`safety_monitor.py`，那是**新鲜度契约**的线，不是保活界。

保活是个**合取**干预：只有在「(a) range 判定那一刻已经超预算」**且**「(b) 被复用的
扫描已过界」同时成立时才会动手。8 轮里 (b) 出现过 26 帧，但 (a) 在这些帧上一次都没
成立（`_over` 在 `fsd_stack.py:984` 是拿 `_tick_cost0`（tick 起点）量到 range 判定点的
耗时，ring 单独只有 253–420 ms，还没过 450 ms 的预算）→ 扫描照常执行、state 记
`scanned`、`keepalive_forced` 计数 0，**没有任何一次 defer 被 `_starved` 挡下来**。
所以两臂跑的确实是同一套逻辑，`travel` / `collision_count` / `off_road` 的差都是噪声。

**但输入并不是无害的**：OFF 臂 `town_1789888682` 有一次 defer 发生在 age **1.552 s**，
把下一帧推到 **2.232 s**——越过 `STALE_RANGE_S = 2.0`，**正是这个下限要防的形状**；
而 ON 臂的每一次 defer 都在 **0.608–0.677 s**，离 1.0 s 的界还有距离。

所以结论只能是：**这组实验证明处理「没有开火」，不能证明它「不会开火」**。要判它，
必须构造一个让 (a)、(b) 同时成立的**可控超预算测试**（假时钟 + 可控耗时），
而不是再加 town 重复次数。object 侧更远：8 轮 object age 最大只有 0.78–1.70 s，
连 2.0 s 的界都没到。

另需覆盖的分支（方案 P1）：冷启动 `age=None`、任务执行中（`runner.busy`）、
输出过期/乱序——只查 `forced` 计数是不够的。

### 2B-3. 饥饿率是 ring 开销的函数（r = 0.895，n = 22）

同一套代码、同一个开关（`BEAMNG_SCHED_KEEPALIVE=0`）：第一轮 off 臂饥饿 23.8%
（`ring_p50` 330–423 ms），本轮 off 臂只有 2.9%（`ring_p50` 283–345 ms）。把全部
22 个带 `range_sched` 的 town 跑次放在一起：

| `ring_p50` 区间 | 帧预算延后率 |
| --- | --- |
| < 310 ms | 0.0 – 1.7% |
| 310 – 350 ms | 0.6 – 6.7% |
| 350 – 390 ms | 8.3 – 15.0% |
| > 390 ms | 27.7 – 39.4% |

`ring_p50` 与延后率的皮尔逊相关 **r = 0.895**，拐点在 380 ms 附近（预算 450 ms）。

所以：**`range` 饥饿是 ring 开销的因变量，不是保底能治的病。** 第一轮把 23.8% → 1.0%
记在保活头上是错的，那也是会话漂移；本轮同一代码的 off 臂自己就落到了 2.9%。
真正能压住饥饿的是把 ring 移出主循环（A4 `BEAMNG_ASYNC_HEADS`，默认关、尚未实车量过），
见 §4 第 6 步。

`BEAMNG_SCHED_KEEPALIVE` 作为**下限**保留（不触发时零成本，触发时防止复用超过
`RANGE_KEEPALIVE_S` / `OBJECT_KEEPALIVE_S`）。但必须说清：它**尚未被任何实验验证过**
——现有对照里它的强制分支从未执行，所以既不能说它是「饥饿的修复」，也不能说它没用。

### 2B-4. 这一轮的坑（写下来免得下次再踩）

一次后台 A/B 任务在会话重启后**没有死**，和续跑脚本同时抢同一台车（两个 benchmark
各自 teleport、各自驾驶同一辆 etk800），`town_1789889000` / `_9006` / `_9171` / `_9172`

Bash 里参数会被原样传下去而报错，之前的「没有 python 在跑」是**假阴性**。

### 2B-5. 这组 A/B 的分辨率：**4 轮/臂根本不足以标定任何差异**

把 8 轮逐轮的里程列出来，臂内差异**远大于**臂间差异：

| 臂 | 里程（m，逐轮） | 均值 | 标准差 | 出铺装帧数 | stall 帧 | 撞车轮数 |
| --- | --- | --- | --- | --- | --- | --- |
| keepalive OFF | 36.3 / 30.9 / 92.9 / 62.2 | 55.6 | 28.4 | 47 / **176** / 0 / 0 | 134 / 165 / 41 / 128 | 1 / 4 |
| keepalive ON | 64.2 / 53.2 / 59.7 / 93.3 | 67.6 | 17.7 | 0 / **147** / 0 / 0 | 123 / 125 / 128 / 62 | 2 / 4 |

* 臂内里程跨度 **30.9–92.9 m（3.0×）**，臂间只差 **12.0 m**；合并标准差 23.7 m，
  **Cohen d = 0.51**（中等效应）。
* 按 α=0.05、power=0.8、d=0.51 反算，**每臂约 61 轮、合计约 121 轮**（≈5.6 h）。
  **这是特定效应量与方差假设下的粗略估计，不是项目固定门槛**：换一个方差更小的场景
  （固定出生帧、关随机交通）它会变小，换一个更小的效应量它会变大。它唯一的用途是
  说明「4 轮/臂不足以标定 12 m 的差异」，不能反过来当成「必须跑 61 轮」的任务量。
  小样本当然证明不了两臂等效；但「结构上无法识别任何差异」同样过强——
  **本次更直接的问题是保活的强制分支从未执行（§2B-2），而不是轮数不够。**
* `collision_count` 是 0/1 量纲（不是计数），OFF 臂 1/4 轮命中、ON 臂 2/4 轮命中，
  Fisher 精确检验 p ≈ 1.0。`off_road` 更是两臂各有一个 ~150–176 帧的灾难轮。
* **可信的是机理量**，它们与臂无关、可复现：`ring_p50` ↔ 饥饿率 r = 0.895（§2B-3）。
  保活「8/8 轮零开火」同样是可复现的读数，但它是**强制分支未执行的证据**，不是效果
  的证据——而且两臂都出现过越过保活界的帧，只是合取条件没同时成立（§2B-2）。

结论：**要判断任何行为开关的优劣，必须先把轮数提到量级级别，或者换一个方差可控的
场景**（固定出生帧、禁用随机交通、缩短单轮）。在做到之前，不要用 town 单轮的
`travel` / `collision_count` 支持任何结论——这也直接支持方案第八条第 4 项。


## 2C. 碰撞的控制层机制（§9 第 4/5 步的证据）

`town_1789886413.json`（keepalive OFF 臂）在 t=28.27 s 撞墙，损伤 0 → 119.7。逐帧：

| t | `fwd_clear`(raw) | `path_occ_frac` | `corridor_open` | `closest_obs_m` | `min_ttc` | `mon_target` | speed | `emergency` |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 26.77 | 3.44 | 0.85 | True | 3.79 | — | — | 2.46 | 0 |
| 27.57 | **1.20** | 0.86 | True | **1.21** | **0.05 s** | **0.0** | **3.54** | **0** |
| 28.27 | **−0.25** | **0.0** | True | 1.21 | 1.69 s | 0.0 | 0.14 | 1 → **damage 119.7** |

注意 27.57 那帧 `mon_target` 已经是 **0.0** —— 监控层（`min_ttc = 0.05 s` → 障碍风险层）**确实
下了停**。所以这次碰撞不是"判据没看见"，而是**判据来得太晚**：车已在 3.545 m/s、离障碍
1.206 m，按 6 m/s² 算需要 ≈1.05 m 刹车距离再加反应时间，物理上已经压线；`brake` 从 0.284
加到 0.7 也来不及。真正缺的是**接近阶段的速度约束**：26.77 → 27.57 这一 tick 里障碍从
3.79 m 收到 1.21 m，而车**从 2.46 加速到 3.545 m/s**。

四个各自独立的缺口（1 已修，2–4 是第 5 步）：

1. **`fwd_clear` 是瞬时值**（**已修**：`5681654` planning guard + `0547368` 接线）。
   历史跑次里 **31 次**单帧从 <2 m 跳到 >8 m（−0.075→16.36、1.65→15.56、1.82→14.02）。
   碰撞那帧 raw 已读到 1.20 m（3.54 m/s 的刹车储备是 2.0 m）却没刹——因为
   `fwd_clear` 只是遥测列，真正刹车的是 `path_grid_clearance_m`，有路径时它覆盖 raw 层。
   日志此前无法区分这两者，现在有 `clear_src` / `fwd_clear_guarded` / `clear_guard` 三列。
2. **`corridor_open` 逃生舱让"路径 86% 被占"在接近阶段不减速**。`safety_monitor` 的
   `path_occ >= occ_stop(0.40)` 停条件被 `and not corridor_open` 短路；
   `corridor_free_band(min_clear_m=3.0, bands=8, max_blocked_bands=3)`
   （`planning/constraints.py:908`）只逐行数空闲格子、再按受阻行数返回 bool：8 条横带里
   至少 5 条没被完全封死即为 True。于是在 `closest_obs_m = 1.21 m` 时它仍返回 True，
   车只被"缓到 `max_speed × 0.55 = 8.25 m/s`"——**高于当时的 3.54 m/s，等于没有降速**。
   横向"某处有自由带"被当成了"我这条路径能走"。

   **它答不了「能不能绕」**：该函数没有计算连续空闲区间、行间连通性或车辆动力学可达性，
   也没有联合本车道合法区域与 drivable 掩码，缺 `grid`/`obstacle` 数据时还会直接
   `return True`。所以**它的 `True` 不能继续当成 strict 模式允许提速的充分条件**。
3. **无边界时 `_perception_off_road_m` 返回 0.0**。代码里两处盲区：`lane_left` 与
   `lane_right` 都是 None → 直接 `return 0.0`；或者两者存在但 `_boundary_lateral` 的
   `cov=False`（边界没延伸到车身位置——27.57 那帧正是
   `lat_left=None, lat_right=None, lane_paired=1` 的"覆盖率不足"）→ `worst` 保持 0.0。
   于是 `off_recover = road_off > ROAD_OFF_STOP_M(2.0)` 永不成立，"车身已出铺装面"
   这个状态在判据里**不存在**。遥测自己的注释也承认这一点（"blind in strict mode"）。
4. **`_path_occupied_fraction` 的 2.5 m 跳过区——是定义边界，不是缺陷**。最初把 28.27 那帧
   `path_occ` 从 0.86 掉到 0.0 归因到"跳过 `d < 2.5 m`"，读代码后修正：2.5 m 以内的路径点
   落在**车身内部**，本来就不该算作"路径被占"，这一跳是路径占用率这个量的定义边界。
   真正的问题不是它跳，而是**近场没有任何一层接手**——现在由第 4 步的 clearance guard
   负责（它看的是走廊/路径净空，不是占用率）。同一帧 `plan_blocked` 报 `no_perception`，
   所以那次 0.0 里也混了"路径整个丢了"这条原因。

## 2D. 无路面证据时的 fail-closed（§9 第 5 步）

### 被推翻的方向：`ego_drivable_coverage`

`a97cdaf` 加的"车身足迹 vs drivable 掩码"看起来正好回答"车在不在路上"，实测不成立：
前视相机看不到车身正下方，**最近 drivable 格子恒定在车头前 3.75 m**（12 个跑次里
一模一样，包括出生帧），所以足迹重叠恒为 **0**，`ego_drivable_coverage` 在所有跑次
上恒返回 0.0（`b35c3e1` 的局部激活规则把它改成 `None`，语义正确但依然答不了问题）。
这是几何必然，不是跑次运气。函数保留，**不要接进判据**。

### 落地判据：`lane.perceived_road_state`（`7876429`）

用 lateral guard 和弯道限速**已经在读的同一个 2–12 m drivable 带**，只换问法：
"它这次答了吗"。三态 `on_road` / `off_road` / `unknown`。

真值用 `edge_over`（地图路沿算出的"出铺装面多少米"，**只当指标**）。在 12 个帧数对齐、
带真值的 town shadow 回合上：

| 分组 | 回合数 | 丢带帧占比 | 最长连续丢带 |
| --- | --- | --- | --- |
| 没出过铺装面 | 8 | 0.0%（7 个）/ 2.8%（1 个） | 0 / 5 帧 |
| 出过铺装面 ≤ 1.22 m | 3 | 0.0% | 0 帧 |
| 出过铺装面 6.96 m | 1 | **50.6%** | **91 帧** |

分离度足够：良性最坏是连续 5 帧（≈3 s @ 1.65 Hz），跑偏那次是 91 帧。带**横向位置**
反而是弱信号（最坏跑次里"带整体离开车身"也只占 0.5–4.6% 的帧），所以判据用的是
"带丢了"而不是"带偏了"。

一个必须说清的限制：**丢带是滞后信号，不是预警。** `off2` 在车压出铺装面 27 帧之后
带才消失，`on2` 晚 6 帧。所以这道门能**兜住**跑偏（不让它以 5 m/s 继续开出去），
不能**预防**第一次压出去；预防要等近场有感知，见第 5/6 步。

### 接线（`safety_monitor.py`，默认关）

`BEAMNG_ROAD_SURFACE_GATE=1` 打开；关着也**照常测量并发布** `road_surface` /
`road_lost_s`，所以可以像别的开关一样做 A/B。分级响应：

* `off_road` → 立即 `degraded` + 爬行（正证据，但不硬停：带是看 2–12 m 前方，弯道会把
  它平移过去，hairpin 上硬停不可接受）；持续 `ROAD_LOST_STOP_S` 才 `minimal_risk`；
* `unknown` 持续 `ROAD_LOST_DEGRADE_S(4.0 s)` → `degraded`；持续 `ROAD_LOST_STOP_S(8.0 s)`
  → `minimal_risk` 停车；
* 单帧丢带**不**动作（否则就是把调度问题换成停车问题）；
* `scene.grid is None`（配置里根本没有 BEV）**不**计时钟——那是另一种故障，归管线
  staleness 规则管，否则无 BEV 的配置会在阈值后停车。

阈值取 4 s / 8 s：良性最坏 3.0 s 在线下，跑偏那次的 55 s 远在线上。

### 实车三轮验证（`BEAMNG_ROAD_SURFACE_GATE=1`，同条件）

| 轮次 | 跑次 | 帧 | `road_surface` | `road_lost_s` | 门开火 | 出铺装帧 | 里程 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | `town_1789890111` | 182 | on_road 181 / unknown 1 | max 0.00 | **0** | 0 | 91.5 m |
| 2 | `town_1789890286` | 180 | on_road 178 / unknown 2 | max 0.00 | **0** | **60（最差 0.60 m）** | 86.4 m |
| 3 | `town_1789890448` | 166 | on_road 165 / unknown 1 | max 0.00 | **0** | 0 | 42.7 m |

**没有一次误停**：三轮共 528 帧，门开火 0 次，`reason` 里从未出现路面门字样，
最长连续非 `on_road` 是 2 帧（远低于 4 s 阈值）。健康跑次上这道门是完全静默的。

### 但第 2 轮暴露了判据的**灵敏度上限**（重要）

第 2 轮车**真的压出铺装面 0.60 m、持续 60 帧**（`edge_over > 0.3`），而
`road_surface` 全程报 `on_road`，门**一次都没动**。原因不是 bug，是几何：

* 判据问的是「2–12 m 前方的 drivable 带**还有没有**和车身的 ±(0.95+0.5) m 窗口重叠」；
* 带是**前方**的读数，车横向出去 0.6 m 时带仍然覆盖车身窗口 → 答 `on_road`；
* 要让它翻成 `off_road`，带得**整体**移出那个窗口，也就是实际需要 ~1.45 m 以上的横向
  偏离 —— 这解释了 §2D 语料里为什么只有 **6.96 m** 那次（91 帧）被抓到，而 1.22 m 级的
  3 个回合一个都没丢带。

所以这道门的准确定位是：**「带丢了」检测器，不是「压线/出路沿」检测器**。它能兜住
6–7 m 级的跑飞（这正是 §1.2 那个撞车场景的量级），但**看不见 0.6 m 级的贴边**。
不要把它当成横向安全网；0.6 m 级的贴边归 lateral guard / 标线投影管。这条必须写进
判据的 docstring，否则下一个人会以为「`on_road` = 车在路面内」。

### 顺带修掉：新遥测列自己犯的同一个错（§5 的原则）

三轮里那 4 个 `unknown` 帧**全部不是**「读了带、带没了」，而是**判据根本没跑到**：
`_evaluate_core` 在「no drivable path」（第 1 轮 idx 4；第 2 轮 idx 99–100）和
「path hold (creep)」（第 3 轮 idx 135）就提前 return 了，于是发布的是 dataclass 默认值
`road_surface=unknown` + `road_lost_s=0.0` —— 和「读了但没证据」**字节相同**，而 `0.0`
读起来就是「路面正常」。这正是方案第七条禁止的「把证据缺失当安全状态」，被我自己的
新列复现了一遍。

修法：加 `SafetyVerdict.road_checked`（默认 `False`，`_road_surface_gate` 调用点置
`True`），**`road_lost_s` 必须和 `road_checked` 一起读**。注意旧跑次（含 §2B 那 8 轮）
没有这一列，所以**不能**回头用它们统计「带丢了多久」。

## 2E. 方案第五条（调度遥测）的覆盖度——**还没做完**

方案要求「每 head 记 eligible_time / dispatch_time / finish_time / skipped /
skip_reason / output_time / age / compute_ms」，并把「没调度」和「跳过」和「worker
没启动 / 启动未完成 / 完成没发布 / 发布没消费」分开。逐条核对现状：

| 方案要求 | 现状 | 落在哪 |
| --- | --- | --- |
| age | ✅ | `meta.head_age_s`（`871f0c4`） |
| compute_ms | ✅ | `meta.head_sched[*].compute_ms` |
| skip_reason | ✅ 文字理由 | `head_sched[*].reason`（`tick 0.62s > budget 0.45s`） |
| skipped（被 budget 跳过） | ✅ | `head_sched[*].state == "budget_deferred"` |
| 没调度 | ✅ | `"no result and not due"` / `"async_idle_no_output"` |
| worker 没启动 | ⚠️ 间接 | 只能从 `head_worker` / `range_worker` digest 的 `busy` 推 |
| worker 启动未完成 | ✅ | `"async_in_flight"` + `reason: in_flight_s=…` |
| 完成但没发布 | ❌ | 没有这个 state；`async_adopted` 把「完成」和「发布」合成了一步 |
| 发布但控制侧没消费 | ❌ | 完全没有；`head_age_s` 只证明 head 产出了，不证明控制循环用了 |
| `eligible_time` | ❌ | 只有 `age_s`（距上次**输出**），没有「何时该跑」 |
| `dispatch_time` | ❌ | 没有 |
| `finish_time` | ❌ | 只有 `compute_ms`（时长，不是时刻） |

也就是说：**12 条里 7 条已落地、1 条只有间接证据、4 条缺失**（§9 第 3 步未闭环）。
缺的 4 条里，「发布但控制侧没消费」是最值钱的——它正好对应 §1.2 那类
「监控层下了停、车却已经来不及」的链路，而现在的遥测无法回答「这个 head 的输出
到底有没有被用上」。补它需要在控制侧记一次「本次 tick 消费了哪个 head 的哪个版本」，
而不是在调度侧再记一遍时间戳。

   方差可控的场景」，或者干脆放弃用 town 单轮指标做行为验收。**建议先做「激活检查 +

5. **逃生舱的速度约束用什么量区分「绕得过去」和「绕不过去」？**（§4 第 5 步）
   `closest` 在「路口杂物该保持速度」和「马上要撞上」两组场景里分别是 **3.750 m 和
   3.789 m**，所以纯距离判据必然误伤前者。可选：
   (a) 加自车速度/闭合速率项（测试场景 v=0，碰撞帧 2.461 m/s，能分开，但**阈值要标定**）；
   (b) 在 `planning/` 新增一个**真正的通道/轨迹可行性原语**，输出
   `FEASIBLE / INFEASIBLE / UNKNOWN`，附证据来源、版本、年龄与失败原因；逃生舱只在
   `FEASIBLE` 时保留地板，`UNKNOWN`/`INFEASIBLE` 时不得用 `corridor_open` 恢复巡航；
   (c) 都不做，改为只在「`corridor_open` 且障碍已在刹车储备内」时降级——但那已被证明是
   no-op（§4 第 5 步），等于不修。

   我倾向 (b)，但**必须说清 (b) 不是给 `corridor_free_band` 加两个字段**：该函数
   （`planning/constraints.py:908`）只逐行数空闲格子再按受阻行数返回 bool，
   **没有**计算连续空闲区间、行间连通性或车辆动力学可达性，也没有联合本车道合法区域与
   drivable 掩码，缺数据时还返回 `True`（详见 §2C 第 2 条）。旧接口可保留兼容，
   **但不能继续把它的 `True` 当成允许提速的充分条件**。

   (b) 需要的新证据是「**连续合法通道 + 已选可执行轨迹 + 动态速度约束**」：车辆宽度、
   转弯能力、转向响应、制动能力、源数据年龄与控制延迟都要有明确来源或保守界限——
   **「不需要标定」这个说法不成立**。也不能用「`v=0` vs `v>0`」两个测试就代替。
   代价：跨 `planning/` 与 `safety_monitor` 两个模块，按提交纪律拆成有序提交
   （先纯新增原语 + 正反例，再接线作行为变更）。

5. **`corridor_open` 逃生舱的近场门**（见 §2C 第 2 条）——**注意：本节原来写的判据
   形式是错的，实测在本链上是 no-op，必须先改设计再实现。**

   原写法：「`closest` 落在刹车储备 `emergency_stop_clearance_m(v)` 以内时逃生舱作废」。
   拿 §2C 的帧回放，它**在真正造成伤害的那一帧不触发**：

   | t | v | `closest` | `reserve(v)` | 原判据触发 | 当时 `mon_target` |
   | --- | --- | --- | --- | --- | --- |
   | 26.772 | 2.461 | 3.789 | 1.505 | **否** | **3.30（逃生舱给的）** |
   | 27.572 | 3.545 | 1.206 | 2.047 | 是 | 0.00（障碍风险层已经归零） |

   伤害是 26.772 那帧的 **3.30** 造成的（车从 2.46 加速到 3.545）；而原判据到 27.572
   才触发，那一帧 `mon_target` **已经是 0.00**（`_apply_obstacle_risk` 归零），所以
   「作废逃生舱」什么都不会改变 —— 车照样以 3.545 撞上去。**原判据只兜住已经停住的
   情况，兜不住造成加速的那一帧。**

   正确的形式要带上**一个控制周期的反应距离**：逃生舱承诺的速度必须在
   「刹车储备 + 本 tick 的行程」之内才合法，即

   ```
   s²/(2·decel) + s·T_tick  ≤  closest − margin      # T_tick ≈ 0.8 s
   ```

   同样两帧回放：26.772 帧允许的上限是 **2.72 m/s** < 逃生舱想要的 3.30 → **作废**；
   27.572 帧允许 0.25 m/s，但那时 `mon_target` 已是 0.00，不需要它再做什么。

   **但这一步是简化模型下的反事实计算，不是结论。** 把 26.772 帧的目标限到 2.72
   不等于车的实际速度会立刻变成 2.72（它当时正从 2.46 往上走），也不等于「下一帧障碍
   约在 1.71 m、刹停只要 0.617 m、还剩 1.09 m」这串数字会在实车上成立——它假设了障碍
   不继续接近、制动能力恒为 6 m/s²、控制无延迟。**不能由此确认一定避免碰撞**，只能说
   这个方向比原判据更可能兜住造成加速的那一帧。要确认必须走离线回放 + 闭环。

   `T_tick` 取 0.8 s（实测 `tick_ms` p95 ≈ 610 ms，留一档）。这个形式只**降低**速度、
   不会新增硬停（作废逃生舱只是撤掉地板，目标退回未抬高的 proximity ease），所以对
   `no_stall` 的风险小于「`not corridor_open` → 硬停」那种写法。验收仍是
   `collision_count == 0` 且 `no_stall` 不恶化，但见 §2B-5：**town 单轮验不了**，
   要在离线回放（可复现帧链）上先证「26.772 帧会被压到 2.72」，再谈实车。

   #### 但这个 cap 还不能直接接线：它和逃生舱的既有职责在同一距离上撞车

   把 cap 拿到逃生舱**故意要服务**的那两个场景上量一遍（`logs/_envelope_conflict.py`）：

   | 场景 | `closest_obs_m` | 逃生舱地板 | cap | 结果 |
   | --- | --- | --- | --- | --- |
   | `test_open_corridor_treats_scattered_path_occupancy_as_soft` | **3.750** | 8.250 | **2.686** | 目标 8.25 → 2.69（3.1×） |
   | `test_corridor_open_never_crawls_to_creep` | **3.750** | 8.250 | **2.686** | 目标 8.25 → 2.69（3.1×） |
   | 碰撞帧 t=26.772 | **3.789** | 3.30 | 2.717 | 目标 3.30 → 2.72 ✓ |

   **`closest` 在这两组场景里分别是 3.750 和 3.789 —— 差 4 厘米。** 所以**任何只依赖
   `closest` 的判据都无法区分它们**：接线就等于把「路口杂物不爬行」那个已经赚到、
   已经被测试钉住的修复重新推翻（那两个测试的注释写得很清楚：`fsd opt21 t=54-60`
   就是被 2–3 m/s 的 creep 拖到刹停-再起步的）。

   真正的区分量是**自车速度 / 闭合速率**（测试场景 `ego_speed_mps = 0`，碰撞帧 2.461），
   或者**横向逃逸是否还来得及**——逃生舱的前提是「有一条自由带，所以我能绕」，
   而 2026-09-20 那次的前提**几何上成立、动作上已经来不及**。注意
   `corridor_free_band` 现在**只返回 bool**，不暴露带的位置和宽度，所以
   「还来不来得及切进那条带」今天**答不了**；而且它连「有没有一条连续的带」都没算过
   （§2C 第 2 条），所以这里需要的不是「暴露两个字段」，而是 `planning/` 新增一个带
   几何与动力学的**可行性原语**（`FEASIBLE / INFEASIBLE / UNKNOWN`）。

   结论：`contact_envelope_speed_mps`（在 **`beamng_autopilot/planner/obstacles.py`**，
   不是 `planning/`）作为原语是对的、已单独提交（`22e825e`），
   但**接线前必须先定「用什么量区分绕得过去和绕不过去」**——这是需要你拍板的事，
   见 §3 第 5 项。**逃生舱的 cap 数值这一步仍然不动**：
   `test_corridor_open_never_crawls_to_creep` 与
   `test_open_corridor_treats_scattered_path_occupancy_as_soft` 固化了"软 cap 而不是
   爬行"这个决定，改它要单独测。
6. **逃生舱的 cap 数值**（`max_speed × 0.55` vs 爬行）是能改变这次碰撞结果的候选杠杆
   （**注意是候选，不是已证结论**）：26.77 那帧障碍在 3.79 m、车 2.46 m/s、`path_occ`
   0.85、`mon_target` **3.30**（= `6.0 × 0.55`，即逃生舱）。若 cap 是 2.0 m/s，
   车**大概率**不会加速到 3.545，27.57 的强制停就更可能来得及——但这是简化模型下的
   推断，同样要离线回放 + 闭环确认。需要单独 A/B，因为它会同时压低 `travel`。
7. **控制周期**：大头是 `tick_ms.ring`（546/601 ≈ 91%），而且 §2B-3 已经证明饥饿率
   是 `ring_p50` 的函数。但**不要预先把它归给 A4**：
   * `_async_allowed`（`fsd_stack.py:187`）只对 `object` 允许异步，`semantic` 仅在
     非 strict 时允许；`ring.grab_ring()` 仍在 `fsd_stack.py:686` 的主流程里
     **同步调用**。
   * ring 计时块**包含的不止相机采集**；LiDAR 两阶段路径还依赖 provider 的
     `range_split` 能力。
   * 所以「开 A4 即达 150 ms」不能预先承诺，A4 也**不是**唯一有效杠杆。

   下一步应按关键路径拆开量：ring 再细分采集 / 预处理 / semantic / object / 结果处理，
   另量 LiDAR fetch/process、BEV、lane、plan、control、日志，**按最大阻塞项决定优化
   对象**（若主要是同步 semantic 或相机 I/O，单开 object 异步解决不了它）。
   见方案 P3。另外要解决文档里「九组含 async」与「尚未测 async」的口径冲突。
8. 上述修完后，再重跑 §12 对照与（若有标签）参考类指标。
