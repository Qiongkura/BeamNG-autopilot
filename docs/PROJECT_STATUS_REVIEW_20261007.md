### 2.3 驾驶失败的记录更细，但新探针需重新确认有效性

复核九份 `logs/experiments/e5_pose_sweep_20261007/d*.json`：

- 共 **311 行**，`reason=no drivable path` 为 **296 行**，占约 **95.2%**。
- 中心条件 46 行：42 行记载配对，26 行来源为 sensor，15 行 `plan_dev_m` 为数值，仅 5 行有正油门；原因包括无路径 31 行、近障碍 5 行、边界恢复 2 行、规划车体越界 8 行。
- 其余八个条件全部为零 sensor 来源、零路径数值；不能把它们统一解释为“已有路径被 4 m 门拒绝”。

**证据链**：原假设：主要阻塞是已有路径被扫掠门拒绝 → 是否激活：九份遥测包含原因、配对、来源、路径和指令 → 可复现输入：上述九份 JSON 的对应列 → 实测结果：多数行更早就无路径 → 结论：不能以扫掠门解释全部失败 → 未知与下一步：需确认实际起始位姿、阶段和观测资格后再建立因果对照。

## 3. 本轮新发现的优先问题

### P0-A：墙钟上限在放置方法中的作用域与返回契约有错误

位置：`beamng_autopilot/fsd_drive.py`。

1. `_wall_hit` 在 `run()` 内定义为局部变量（约第 2247 行），却在独立方法 `_prewarm_and_place()` 中直接调用（约第 2178 行）。该方法没有对应参数、局部定义或模块定义。执行到这里会发生 `NameError`。
2. 方法外层捕获所有异常，并在打印 `pre-warm skipped` 后返回 `_pw_out, _percep_ok, 0`。调用方依据第三项判是否终止，因此异常可能被作为非终止结果返回，失去 strict 放置失败的正确分类。
3. 超限分支写的是 `return 3`；调用方却解包三个返回值。即使先修正变量作用域，这个分支仍不符合方法的三元组返回契约。
4. 当前 `tests/test_fsd_wall_cap.py` 主要检查源码字符串存在，不能验证上述分支的实际行为。

建议将截止时间／检查函数显式传给放置方法，所有返回使用同一三元组契约，strict 的异常与未放置状态明确返回失败并走收尾。验证应使用注入时钟和假连接，实际执行正常放置、放置超时、行驶超时及异常分支；不能只断言有两处字符串。

**证据链**：原假设：内部上限在两阶段均正确生效 → 是否激活：CLI 暴露上限，两个方法都引用检查 → 可复现输入：上述方法、调用方和测试文件 → 实测结果：源码存在跨方法局部变量访问和返回值形状不一致 → 结论：内部上限修复尚未完成，E5 的 strict 放置资格需要重核 → 未知与下一步：本轮是静态作用域检查，没有重新运行游戏；先修并用确定性分支验证，再开展实机复测。

### P0-B：9 份输出文件不等于 9 个等条件、有效的位姿实验

发现三个独立问题：

- 放置阶段会执行感知对齐的再次 teleport。预注册的 CLI 位姿未必是开始驾驶时的实际位姿。例如 `d0.0_y10.json` 首行航向约 **−13.07°**，而脚本请求 **−3°**。目前不能直接把标签 y10 当作实际 +10°。
- `d0.5_y0` 只覆盖约 **5.0 s**，`d0.5_y10` 约 **13.5 s**，`d1.0_y5` 约 **2.3 s**；其它记录约 24–25 s。论文仍写每姿态行驶 25 s。
- 运行器只要文件存在就跳过，执行后也只凭文件存在计成功。旧的短运行、失败写出的遥测和配置不同的产物均可能计入“完成”。

必须记录请求位姿、放置前后真实位姿、位姿误差、放置状态、暖机时间、测量阶段时长、配置摘要、退出码与截止原因。实验可以保持生产 strict 放置行为，但此时应研究“请求位姿经过生产放置后的表现”，不能声称驾驶阶段只改变了固定起始位姿。若要研究严格固定的真实起始位姿，应设计显式的探针契约，不能隐式绕过生产安全检查。

**证据链**：原假设：完整 3×3 实验只改变真实起始位姿且曝光相同 → 是否激活：九份文件存在，但运行器以存在判成功 → 可复现输入：`scripts/m5_pose_sweep.sh`、预注册、九份首末遥测、放置实现 → 实测结果：航向被改、测量时长不齐、跳过规则没有验证摘要 → 结论：支持“九条件已有输出”，不支持完整等条件位姿因果结论 → 未知与下一步：固定探针合同与输出资格后只补无效项，不改写旧结果。

### P0-C：无人值守运行器没有遵守进程归属与 PowerShell 约定

`scripts/m5_pose_sweep.sh` 的 `cleanup_games()` 枚举 `game_pids()`，随后对每个 PID 执行强制终止。注释称“所有权差集”，实际没有启动前快照、创建时间或归属校验；可能结束用户已有的 BeamNG 会话。

第二路段日志 `logs/experiments/_e5_mountain.log` 反复出现 `.venv/Scripts/python.exe: No such file or directory`，截至本轮读取，没有 mountain 的遥测输出目录。项目本身的 `.venv/Scripts/python.exe` 确实存在，日志支持运行入口／工作目录解析失败，不能把这次失败计为山路驾驶结果。

应迁移为项目约定的 PowerShell 7 入口，基于脚本位置解析项目根和解释器；先做解释器、文件、端口和运行归属检查，失败立即给明确状态。复用 `collection.game_procs()`／`close_started_game()` 等已有机制：只清理自己启动且创建时间匹配的实例，不能按名字清全部进程。

**证据链**：原假设：运行器可安全复用且第二路段已进入测量 → 是否激活：已提交脚本存在，第二路段有执行日志 → 可复现输入：脚本清理函数、mountain 日志、解释器存在检查 → 实测结果：清理无归属筛选，第二路段反复找不到解释器，没有遥测 → 结论：执行基础设施仍是自主运行的实际阻塞 → 未知与下一步：没有修改／执行该运行器；先修入口和所有权，再串行验证。

### P1-D：后台配置没有接上新训练预算与初始化

训练器和 `rounds` 的 CLI 已支持 `--total-steps`、`--init`；`train_cmd()` 也会传递。但 `LoopConfig` 的字段没有 `total_steps`、`init`，`LoopConfig.load()` 会丢弃未知键，`rounds_args_from()` 也没有向参数对象传递它们。

因此，手工 `rounds` 可以使用新配方，后台 `run` 配置还不能自然继承这两项。预算缺失时会回到旧行为，不能把训练器接口实现完成等同于后台自主训练接线完成。

另一个缺口是自动来源：后台采集主入口仍生成人工复核队列，原生 annotation 不完整的数据不能直接进入合格线监督；受控场景生成、逐通道认证和自动换场景流程应显式接入已有控制器。不能删除资格门或把未知改成背景来制造连续学习。

**证据链**：原假设：后台入口已支持新采样预算和持续初始化 → 是否激活：训练器和 `rounds` 实现已存在 → 可复现输入：`controller.LoopConfig`、`LoopConfig.load()`、`rounds_args_from()`、`train_cmd()`、`collect_once()` → 实测结果：配置与转换层缺字段，采集仍走复核队列 → 结论：已有组件可复用，但无人值守学习链尚未接齐 → 未知与下一步：本轮未触发后台任务；新增配置契约并证明值进入实际训练命令与 checkpoint。

### P1-E：第二地图认证失败不能直接证明原因只在引擎

现有 west_coast_usa 报告中，六站被正确隔离。点名的 `known_line_a0s0` 不仅 annotation 线像素为零，还包含 ROAD 在 0/6 帧达到资格、外观对齐缺少支持、覆盖为 UNKNOWN 等问题。这足以说明本批不合格，尚不足以排除相机朝向、取帧、类别映射、材质引用和可见性等其它原因。

官方材质格式允许 `annotation` 分类字段，Camera 支持颜色、语义标注和深度输出。因此可以优先用隔离的小型场景做自动探针：一个已知材质的可见漆线、明确无线对照、遮挡对照，逐项检查渲染图、类映射、有效路面与帧一致性。这是可检验的研发方向，不是“改字段必定成功”的保证。[材质文档](https://documentation.beamng.com/modding/file_formats/materials/)、[Camera 文档](https://documentation.beamng.com/beamng_tech/sensors/camera/)

**证据链**：原假设：本批失败仅由地图引擎标线类别导致 → 是否激活：生成与原生采集都已尝试 → 可复现输入：WCU `scene_report.json`、结果文档和公开接口说明 → 实测结果：线、路面、对齐多项不足 → 结论：支持“当前第二地图生产未通过”，不支持所有其它原因已排除 → 未知与下一步：用小型受控素材探针排因，整个过程无需用户人工标注。

## 4. 推荐下一阶段顺序

1. **修复执行和测量资格。** 完成墙钟分支、返回契约、strict 异常退出、归属清理与 PowerShell 入口；验证请求姿态是否真正保持、测量时间是否足够。
2. **定位车道为什么丢失。** 对每一帧保留“图像标线 → 实例 → 左右角色／配对 → 铺装资格 → 路径 → 安全仲裁 → 最终指令”的数量与拒绝原因，区分配对失败和配对后被否决。保留绝不倒车、绝不压线和感知横向参考约束。
3. **接齐免人工训练闭环。** 将初始化、步数预算和自动真值生成／认证接入现有后台入口；来源失败自动隔离、换合格场景，不把“请用户标注”作为默认出口。
4. **开展一轮有明确问题的学习。** 针对可信开发集里一种主要错误自动生成新训练场景，与原基线共享初始化／步数／种子；同时比较召回、精度、身份和负例误报，而非只看 loss 或条件化高分。
5. **验证模型收益能否进入驾驶。** 先离线几何正反例，再独占 Tech 的小型闭环验证；通过后才扩大道路与光照范围。已消费最终集不重新调参使用。

这些建议来自已经观察到的接口缺口和失败链。完成后仍不能保证每轮模型改善；验收应允许“无收益”和“来源不合格”，并能解释原因。端到端与图像 RL 可以保留为后续研究方向，目前应先让一条可信感知链在小型场景内持续工作。
