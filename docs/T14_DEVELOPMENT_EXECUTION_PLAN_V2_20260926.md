## 3. 共同数据与指标契约（S1–S3 的实现依据）

### 3.1 统一的帧清单

复用 `experiments/manifest.py`、`credentials.py`、`spatial.py`、`final_set.py`。
标定与评价都消费经过审计的同一份清单，禁止各自遍历目录再自己计数。

每条至少携带：原始路径、内容哈希、标签哈希、图像尺寸、map/source_id/view/exposure、
位姿及其是否缺失、相机内外参及摘要、标签凭证/rank、逐通道有效性、split、用途、
重复/冲突/拒绝原因、模型训练关系。

- 同 RGB 内容且标签、几何和资格一致：只计一个评价样本，保留全部来源别名。
- 同 RGB、标签不同：记录冲突；有明确修订继承关系时按已确认版本选择，否则隔离。
  不能因路径排序、修改时间或“后读到”而静默覆盖权威标签。
- 同 RGB、尺寸/相机/位姿等身份不一致：先隔离，不把相同像素强行解释为不同独立样本。
- 去重不会创造独立性；同曝光多视角、同路段相邻帧及空间邻近继续按现有规则审计。
- 缺元数据写 UNKNOWN；不从目录名猜地图，不把“没发现冲突”当成“证明独立”。
- 校准/开发与最终集用途要明确。136 帧已反复诊断，不得重新包装为未使用最终集。
  可以复用现有 dev split 并显式记录 calibration/search 用途，避免隐式新建一套划分逻辑。

### 3.2 标注权威性与评价资格

本批 136 帧按用户决定使用为权威真值，凭证从数据集读取；新增字段不能无故使其失效。
此决定不授予其他零标线目录 verified 资格，不消除训练泄漏，也不把 255 变成背景。

训练资格、测量资格、晋级资格分开记录。非 verified 数据可按已有规则用于研究，
但不能因为 CLI 写了 `human_revision` 或省略 research flag 而获得晋级资格。

### 3.3 候选统计先累加计数，再算比率

需在库中提供可复用的计数/聚合接口，候选探针产生逐帧计数，各入口调用同一实现。
具体文件可复用现有模块；若无合适位置，可新增 `experiments/candidate_metrics.py`。
该文件名是建议，不是现有接口。不要在多个脚本各复制一份公式。

设评价 ROI、类别及有效区域沿用已审计的协议：

| 计数 | 精确定义 |
|---|---|
| P | 真值明确存在漆线的合格帧集合；逐帧判断，不能因为同组另一帧有线就全部纳入 |
| C | P 内由实际感知链产生的全部纳入评价的漆线候选数 |
| R | C 中其自身所在侧有可用真值参考的候选数 |
| M | R 中满足冻结匹配条件的候选数 |
| L | M 中预测与参考均有可判左右角色的候选数 |
| A | L 中左右角色一致的候选数 |

固定公式：覆盖率 = R/C；身份匹配率 = M/R；角色一致率 = A/L。
分母为零时比率为 null，并附适用性/原因。M 必须是 R 的子集，不得把无参考候选的匹配
混入分子。候选数量为整数相加，不能把不同目录的数量或比率平均后当总体。
同时报告 micro（计数汇总）、macro（明确单位）、每场景、最差场景和每 seed，主门使用哪种
写入协议；本轮总体主口径采用计数汇总，单坏场景/seed 仍须单独判定。

参考有效性复用现有 `MIN_REF_PX`、投影和匹配容差，并写入新协议快照。
有真漆线却投影失败、相机缺失、探针异常，属于缺证据，不能改成“无线”后排除。
场景内完全可测却没有可用参考匹配时保留计数和失败原因，不能通过过滤困难候选提升覆盖率。

候选包含哪些 kind/source，必须明确冻结：区分漆线候选与合法道路外沿；记录已有 learned、
颜色提取、虚线恢复等来源，不能为了提高分数临时删除困难来源。

### 3.4 UNKNOWN、零值与不适用

输出需要区别：`measured`、`not_applicable`、`unknown`、`unverified_labels`。
可沿用原有 JSON 结构添加适用性说明，不要求粗暴替换全部历史字段。

- 确认真无线且参考完整：标线 recall 和候选参考覆盖不适用，不能永久记为缺测阻挡所有实验。
- 真值有线但模型没预测：recall 为实测 0；身份率的零分母另记清楚。
- 真无线却预测了标线：precision 等有分母的统计仍是真实失败证据，不因“无线”而一律跳过。
- 缺标签、无相机、投影失败、探针异常：UNKNOWN，不能按不适用放行。
- `not_applicable` 只能由可信输入和冻结任务范围派生，CLI 不能自行写入以旁路硬门。
- 无线场景不进入有线参考覆盖门，但仍需独立负例/路面边界任务评价。若只有诊断指标，
  没有完整任务验收规则，R2 报告保留相应缺口，不宣称无线驾驶能力已合格。

### 3.5 负例指标的资格和分母

复用现有 `negative_scenes.py`，保留精确计数层；在帧清单和评价接线处强制资格：
verified、漆线监督完整、评价区域非空且无 UNKNOWN、无真标线，才能成为合格负例。
engine/agent/unknown 来源的“标签全零”不构成确认无线；混合来源分开计数并报告排除量。

- 假线帧率：至少 1 个预测漆线像素的合格负例帧数 / 合格负例帧数。
- 假线像素占比：合格负例的假线像素总数 / 这些帧评价区域的总像素数。
- 路外假线比仍使用已知区域内预测标线像素为分母；不能与前一个占比混比。
- 旧产物没有计数或凭证时保持 UNKNOWN；不得从 `gt_line_px=0` 补造“干净帧”。
- 本轮负例指标先作为版本化诊断接入判定文件/看板；没有独立标定前不新增随意阈值。

### S3：硬门、适用性、协议版本与重放

**修改落点**：`experiments/gates.py`、`protocol.py`，`m5_seg_autoloop.py` 的
rounds/evaluate/replay、`m5_final_set.py`，对应协议文档/JSON。

1. 新增字段必须进入实际判定，不只写进配置。总体、逐 seed、逐场景保持相同定义。
2. 将场景候选下限 30 接到真正消费路径。新协议明确它的计数对象为身份率实际分母 R，
   同时显示 C/R/M；不能用 30 条总候选、其中只有 1 条可判，冒充足够身份样本。
   这是对旧声明的明确化，须写新版本。30 是现有工程下限，不能视为 30 个独立统计样本。
3. R<30 的有线场景记录样本不足；无参考真负例按 §3.4 处理。角色分母 L 也必须明示，
   L=0 为 UNKNOWN；非零但很小时标低样本，不宣称高置信。若另加角色样本下限，先标定并版本化。
4. 逐场景候选覆盖/身份/角色接入合格场景的门控，别只存到 `scene_candidates` 就结束。
5. 输入/版本不一致、缺证据、实测违反、研究来源限制分别记录；总体决策沿用已冻结的优先级，
   即使缺证据优先，也必须保留同时出现的真实失败，不能只输出一个笼统状态。
6. 新协议建议 v5、新阈值文件建议 v4；若接手时已有后续版本则顺延。
   原 v4/v3 文件只读，新文件记录所有分母、适用性、负例诊断、计数下限及聚合方式。
7. 旧判定按其嵌入协议重放；缺新计数字段时说明“无法用新口径重判”，不能给旧记录补 0。
8. 人读协议中 §4.5 与 §5.5 的“已标定/未标定”等冲突一并消除；JSON/hash/代码一致。

**阈值策略**：身份 0.60、覆盖 0.80、角色 0.70、line recall 0.70 等现值保留为候选要求。
去重、分母变更、隔离审计后在新校准记录中重新确认适用性；确认前不宣称已完成标定。
不得根据某个候选差一点过门而降低阈值。没有足够独立校准证据就标待标定并阻止相应晋级。

**验收**：小样本、不适用、未知、坏 seed、坏场景、旧协议、新协议均有确定性正反例；
在线判定与 replay 的状态、原因、计数一致。R2 仍需最终集确认，不由硬门通过自动替代。

### S4：负例记录与学习可视化

**修改落点**：`negative_scenes.py`、帧清单加载/`m5_seg_eval_matrix.py`、
`m5_seg_autoloop.py` 的判定产物、`m5_seg_dashboard.py`，按实际需要复用 monitor 模块。

**数据流**：原始帧/计数 → 评价结果 → 判定 JSON → 现有事件及只读看板。
负例资格由 S1 已落实；本包负责将其诊断与排除原因传入判定产物和界面。
看板不重新计算指标，不另建驾驶控制协议。

| 面板 | 必须展示 |
|---|---|
| 本轮身份 | commit/dirty、run、dataset、协议/阈值、模型完整路径与哈希、实际设备 |
| 数据入口 | 生成/复核/入训/评价四个计数，去重、冲突、来源 rank、已见组、空间 UNKNOWN |
| 学习过程 | step/epoch、train 与 dev loss、实际样本和步数、配方激活情况、checkpoint 变化 |
| 比较结果 | 同 seed 两臂，micro/macro/最差场景，C/R/M/L/A 和分母；未知与不适用分开 |
| 无线诊断 | 合格/被排除帧数，严格假线帧率、像素占比及分母，明确“诊断，不直接晋级” |
| 错误定位 | 同帧真值/生产/候选叠图，掩码、候选、投影与角色，点击可追溯原帧 |
| 资源与判定 | GPU/CPU/内存/磁盘、阶段耗时、暂停/失败原因、硬门与研究结论分别显示 |

无数据展示原因，不画假零值曲线。图表可抽稀，统计与导出保持原始记录。
历史数据没有新字段时显示“旧协议未记录”。训练步骤轴与硬件时间轴分开。
**验收**：一个真实新 run 能从图表追到数据/权重/判定；页面刷新不重复计数；
无模型改善时也能清楚展示失败原因。本轮新增可视化需做页面实际检查，不仅检查 HTML 文件存在。

### S5：后台提议与资源管理补漏

**修改落点**：`experiments/proposer.py`、`controller.py`、训练器参数接线、监督器。

- road-only 或标线监督已屏蔽时，线损失因子判为 inactive，禁止占用训练预算；
  记录“提议/实际参数/实际损失项/生效步数”，不能只看命令行有参数。
- 复用已有逐 epoch 清理，不让产物保留破坏磁盘保护；可进一步按需求实现保留策略，
  至少保存恢复 checkpoint、选择 checkpoint、评价证据及所有者信息。
- 不动历史验收产物；清理只作用本任务拥有、已验证绝对路径且处于允许目录的中间文件。
- 无收益停止按有意义且成功完成的实验计数；无效因子、缺标注、资格失败归单独原因，
  不作为“模型已经没有提升空间”的证据。
- 中断恢复校验数据、配方、协议与 checkpoint 身份；完成 seed 不重复训练，未完成恢复正确步数。

**验收**：road-only + line-loss 提议的真实训练调用为 0；资源门拒绝不伪造训练完成；
因子有效时能看到 optimizer step、权重差异和正确的耗时/预算记录。

### S6：两条定向学习实验（S1–S3 通过后）

先用通过准入的训练数据与固定开发集做小规模检查，再执行成对 seed。不是重新跑耐久。
两臂共享起始权重/初始化、划分、优化器、有效 batch、训练步数与评价路径，改变一个因子。
选择 checkpoint 的规则在实验前写明；best 与 last 分开报告，不准结果出来后挑更好的一种。

**E1：困难负例组成**

- 对照：固定训练配方；实验：用已确认的土路/易混淆纹理负例替换固定比例的训练样本。
- 两臂样本预算与优化步数相同，记录独立样本数、重复采样和每类曝光次数。
  如果要研究“数据量增加”，另开实验，不与组成变化混在同一结论里。
- 评价：负例误报、真实标线召回、路面/铺装约束及候选几何；减少假线不得以全不画线获胜。
- 新训练负例不得取自当前固定开发/校准/最终评价帧或其空间邻近段。

**E2：路口/弯道漏检**

- 先查看 S2 的错误归因。若主要是候选提取/投影/角色错误，先做对应代码实验，冻结模型；
  若主要是掩码漏检，再选择困难正例采样或单个损失参数实验，其他因素固定。
- 核查 `vision/seg_losses.py` 的实际公式：现实现分母含 `alpha*FP + beta*FN`。
  整体 Tversky 权重与 FP/FN 相对权重不是同一个量；禁止照搬“权重 2 就是压 FP”或
  “beta<1 就提升召回”的口头判断。先用合成 FP/FN 例子验证当前实现和梯度方向。
- 评价逐场景召回、精度、候选身份、负例误报与时延，保留坏场景，不以总体均值掩盖。

**执行规模与自停**：起步沿用最低 3 个配对 seed；只作探索且明确样本有限。
是否增加到 5 个或更多根据效果量/区间与预算决定，不能反复更换 seed 直到显著。
运行前冻结最小有意义收益与非劣余量，保存所有配对差值；无收益/证据不足是合法结果。
看板必须能证明真实反向传播、optimizer step 和权重更新，不能以生成了目录证明学习发生。

### S7：独立最终确认与 Tech 验收（有条件执行）

候选先通过可信开发评价，再冻结未被搜索/标定访问过的最终场景。复用 final_set 的
封存、一次访问账本、协议/数据/权重绑定；最终集失败后不得对同一集调参再叫独立确认。

R2 要逐项列出适用场景、来源资格、硬门、独立性与未测项。无线边界等任务只做过诊断时，
不能签收其驾驶适用性。没有合格候选则停在 R1/研究阶段，不为完成计划降低要求。

R2 通过后执行 Tech：先固定模型的影子记录，再在有导航目标的限定场景低速闭环。
核对现有入口是否控车，命令中记录实际 runtime/goal/sensor/strict/模型/控制权。
禁止假定“shadow”名字就代表没有车辆控制。

验收强制刷新后新源被最终控制消费；几何有空隙/可安全执行正反例；漆线优先与无边界停车；
路面门 TP/漏检/误停；全 tick 时延和源年龄；碰撞、压线、倒车、出铺装、分类停车时长。
测量覆盖不足的指标列 UNKNOWN，不能把未测写成零事件。

### 6.1 多子 agent 并行执行方案

可以并行开发。当前协调会话允许主 agent 加最多 3 个同时工作的子 agent；
其他执行环境应先核对自身额度。独立任务适合并行，依赖尚未完成的接口和共享文件需要协调，
参见 [OpenAI 多 agent 文档](https://developers.openai.com/api/docs/guides/responses-multi-agent)。
本节是待执行分工，添加方案不代表已启动开发或训练。

#### 第一批：主 agent 集成，3 个子 agent 分别开发

S0 先冻结基线、数据字段及 C/R/M/L/A 计数契约，再启动下面的独立任务。

| 执行者 | 工作包与独占文件范围 | 必须交付 |
|---|---|---|
| 主 agent | S0、接口冻结、集成；独占 `scripts/m5_seg_autoloop.py`、`m5_identity_calibration.py`、`m5_seg_eval_matrix.py`、最终集入口与总方案 | 基线清单、接口契约、接线、资源队列、集成验证及八项报告 |
| 子 agent A：数据资格 | S1；`experiments` 下 manifest/credentials/spatial 相关模块及对应专用测试；具体已有文件先登记 | 唯一帧清单、重复/冲突证据、来源资格与空间关系判定；UNKNOWN 不冒充独立 |
| 子 agent B：候选计数 | S2；计数库（按需新增 `candidate_metrics.py`）、`scripts/m5_marking_identity_probe.py` 及专用测试 | C/R/M/L/A 原始计数、逐场景输出、加总后求比率、已知无参考与 UNKNOWN 区分 |
| 子 agent C：门控协议 | S3；`experiments/gates.py`、`protocol.py` 及专用测试；不修改主 agent 的入口 | 分母/样本量门、场景适用性、旧 schema 兼容、协议版本与确定性判定反例 |

目录名均相对项目根；实际修改前登记完整文件路径。A/B/C 可以基于冻结契约和确定性
样例开发，真实输入接线由主 agent 在依赖完成后执行。若发现必须改变契约，先把变更
发给主 agent，由其统一更新受影响任务；不得各自推测字段含义。

#### 第二批与阶段依赖

- 第一批合并并通过 D1 后，释放的子 agent 分别做 S4 可视化、S5 有效因子/资源调度、
  独立复核 T01–T16。先登记文件归属；S4/S5 同时涉及 autoloop 时，子 agent 提供库接口
  和接线建议，主 agent 修改该入口。
- 主 agent 接线 S4/S5 并验证后才进入 S6。修复无效指标期间不能据此选模型、调阈值。
- S6 的训练、评估、时延复测由主 agent 排队执行；子 agent 可以同期检查代码、文档和
  已完成结果，但不能另开 CPU 重活或争用 GPU。
- S7 的最终集和 Tech 驾驶严格依赖前面的签收，不以并行提速为由提前访问最终集。

依赖顺序：**S0 → A/B/C 并行 → 主 agent 集成 D1 → S4/S5/复核并行 → 集成 → S6 → S7**。
约 3 小时窗口优先完成第一批与可复现评价证据；并行不保证完整训练、最终确认和驾驶
都能在此窗口完成，仍采用第 8 节分级签收。

#### 工作区、文件与资源规则

1. 子 agent 默认共享文件系统，并不会自动获得独立 checkout。代码开发优先分配独立
   Git worktree 和 `codex/` 分支，全部来自同一冻结基线；每个文件只能有一个写入者。
   同一大测试文件也不能多人同时修改，优先增加任务专用测试文件。
2. worktree 不会自动带入现有未提交和未跟踪文件。主 agent 审阅并按白名单传递任务所需
   补丁/新增文件，记录基线 SHA、补丁和文件哈希；不得用 `git add -A` 打包所有用户工作，
   不复制备份目录和整套运行产物。遇到既有未提交修改先阅读并保留。
3. 每个工作区使用独立临时输出/run-id；复用现有路径配置和测试隔离方式，读取权重及
   数据时明确来源。不能让多个 agent 写同一个 run、live.json 或控制命令文件。
4. 主 agent 维护测试/训练/测量队列。完整 pytest、深度离线验证、训练、大数据审计和
   p95 测量串行；计时期间其他 agent 只进行不争用计算资源的工作。普通定向测试也
   先登记，不能污染测量。一个训练进程、一个驾驶控制者分别有唯一责任人。
5. 每批子任务独立交付可审阅 diff；主 agent 按模块和依赖顺序合并，测试随模块改动走。
   不把 3 个 agent 的全部改动压成一个提交；每个提交必须满足第 7 节可运行和回归要求。
6. 复核者与该项实现者分开。复核发现的缺口回派原实现者，不让复核者直接覆盖他人文件。
   子 agent 不自行替换生产模型、调整冻结阈值、消费最终集、启动驾驶或推送。

#### 可直接派发的任务说明

主 agent 先填入实际基线、补丁哈希、文件清单、冻结契约位置与输出目录，再派发：

> A：完成 S1 的库实现与专用测试。只修改登记的数据资格文件；使用冻结基线和接口。
> 交付唯一帧/冲突/凭证/训练与空间关系反例，不把未知标成合格。需要脚本接线时交给
> 主 agent。申请队列后执行定向测试，不启动训练、驾驶或完整回归。
