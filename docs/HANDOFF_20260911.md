## 三、本轮实现的改动：虚线边界恢复

`beamng_autopilot/vision/lanes.py`：

- `group_world_fragments`（纯逻辑，可单测）：方向一致 `|cos| ≥ 0.94`、横向共线
  `≤ 0.45 m`、纵向间隙 `≤ 8 m`、链跨度 `≤ 60 m` 的片段并成链。
- `recover_dashed_boundaries`：每条链合成**一条长边界**。
- `_mask_fragment_polylines`：把掩码连通域回投影成世界片段。
- 接线在 `Segmenter.detect_lines`，8 项单测在 `tests/test_dashed_recovery.py`。

**为什么需要它**：城镇 `line` 类不是几条连续长线——每帧 **p50 17 个连通域**、高度
中位数 **7 px**，只有 **23.8%** 能过提取器的形状门（`h≥18`、宽度、填充率）。被丢的
是**真漆画**（被丢像素 65% 落在 GT 上），但都是**亚米级碎屑**（被丢 `unknown` 标线
世界跨度 p50 0.60 m），不携带边界几何，于是本车道只剩一侧边界、永远配不成对。

**实测（3 集 654 帧，v13b）**：

| | 配成双侧本车道 | `lane_sel=sensor` |
| --- | --- | --- |
| 归并前 | 20.8% | 45.1% |
| **归并后** | **43.0%** | **55.5%** |

关键：归并出的边界**本身足够长**，是**凭自身几何合法**跨过
`LANE_PAIRED_VISION_MIN_SPAN_M = 6.0`——**跨度门槛没有被降低**。

**接线时的坑（已量）**：归并必须只吃**学习掩码**，不能吃
`white_mask = 学习 ∪ 经典CV亮线`。喂并集只有 23.9% 配对率，喂学习掩码才是 43.0%
——CV 并集里的纹理亮边不是漆画，会污染分组。经典 CV 通路保持"只保底不新增功能"。

## 四、不要重走的坑

1. **降 `LANE_PAIRED_VISION_MIN_SPAN_M`**：3.2 m 的短配对可以在"每个点都离车很近"
   的同时让中心偏离导航路线好几米（runs 42/47/52）。实测降它能把配对率"提"到 41.9%，
   但放行帧里有 18% 不在车道内——**聚合指标不能否证一条为尾部风险存在的守卫**。
   该门现已补单测（`tests/test_lane_fusion.py`）。
2. **放开标线提取守卫**：守卫是承重的（放开 `min_height` 会让"标线"从 3.0/帧涨到
   57.9/帧而配对率不动）。
3. **放开候选门控**：`*:side` 那些被丢标线的 GT 占比是 **0%**，门控正确。
4. **时序延续（last-good hold）**：掉线是**长时缺失**——16 段、185 帧、101.6 秒，

## 九、`stale sensor` 根因确认，以及与并行进程的协同（2026-09-11 上午）

### 根因（由新加的 freshness 遥测一次定位）

用 `8303312` 新增的逐帧 `freshness` / `head_age_s` 字段跑了一轮城镇（`town_1789092137`）：

判 stale → 失败关闭停车。

间隔，而真实墙钟间隔是「暂停仿真 + 规划 + step(0.75 s)」约 0.5–0.9 s。**假设是对的，我的模型错了。**

## 十一、虚线恢复已做便宜并默认开启（2026-09-11 10:47，commit `f39d298`）

### 性能：17× 提速，且瓶颈与我预想的不同

1. `back_project` **每次调用都重建相机位姿**（3 个 cross + norm），而每帧要调 ~542 次；

## 十五、死锁真因：被拒的横向修正不该升级为整车急刹（commit `66e02cd`，已实车验证）

## 十九、`_mirror_right_ok` 的近场判据在几何上不可满足（2026-09-11 离线，决定性）

### 几何事实

用前视相机模型（front_main，536×403，`cx=268 cy=201.5 fx=fy=316.3`）把图像各行反投影到地面：

| 图像行 | 反投影纵向距离 |
| --- | --- |
| v=402（**最底行**） | **3.59 – 3.78 m** |
| v=343 | 4.4 – 4.7 m |
| v=283 | 6.3 – 6.9 m |

**相机能看到的地面最近只有 3.59 m**；右侧车道线（横向 ≤ −1.2 m）在图中最早的可见纵向距离也是
**3.592 m**。这与上一节实测的右边界起点中位 **+3.72 m** 几乎完全吻合——**那些"缺失的近场点"
不是检出失败，而是根本不在相机视野内**。

### 结论：该判据死路

`_mirror_right_ok` 要求右边界在 `LANE_RIGHT_MIRROR_NEAR_M = 3.0 m` 内**有 ≥2 个点**，
而相机物理上看不到 3.59 m 以内的地面 → 对于正直行驶的车，这条判据**永远不可能通过**。
这解释了：

- 420 次拒绝**全部**是 `no near points`；
- 放宽到 `ext 4.5` **毫无变化**（3.59–4.5 m 区间内通常只有 1 个点，仍 < 2）；
- 放宽到 `ext 6.0` 才生效，但引进的是横向参考错误的"车道"（见上节）。

**即：严格模式赖以兜底的单边右侧镜像路径，实际上被一条几何上不可满足的判据关掉了。**

### 但"放宽窗口"仍然不是修法——真正缺的是另一个**可验证**的判据

上一节的实验已证明：naive 放宽到 6.0 m 会让中心横向从 −0.19 漂到 +0.16 m。原因是那些
帧里被当成"右边界"的线横向只有约 −1.6 m——**那是中线（或左边界），不是右边缘**；
把它按"右侧 1.75 m"镜像，车就被放到了错误一侧。

所以缺的判别不是"线靠车多近"（不可见），而是"**这条线到底是右边缘还是中线/左边界**"。
可验证的候选判别：

1. 线的横向量级（右边缘通常 ≳2.5 m 右；中线约 1.6–1.8 m）；
2. LiDAR 走廊的右墙/右边缘与它的同侧关系（`build_lidar_corridor` 已有该信息）；
3. 该线是否与**已确认的左侧/中线**成对（配对信息里本来就有 left/right kind）。

这三条都**不依赖车旁 3 m 内的像素**，因此是几何上可用的判据。**下一步应在此三选一（或
组合）实现，并用影子集量化：可用率提升的同时**中心横向必须仍落在本车道**（≈ −1.75 m）。

**不要**再把 `LANE_RIGHT_MIRROR_NEAR_M` 当作调参对象——它不是阈值太紧的问题，
而是测量窗口位于相机盲区。

## 二十、镜像路径的可用性无法从这批数据解锁；杠杆转向配对率（2026-09-11 离线）

### 用"可达窗口 + 横向量级"替代盲区近窗判据的受控实验

判据改为：在**相机可达**窗口（纵向 3.3–10 m）内取右边界点的横向中位，要求其 ≥ `edge_min` 偏右。
673 帧，验收指标 = 镜像中心落在本车道（|lat − (−1.75)| < 1.2）：

| 变体 | `chosen` | 中心 lat 中位 | 车道内比例 |
| --- | --- | --- | --- |
| 基线（3.0 m 近窗） | 40.3% | −0.19 | **20.3%** |
| edge_min=0.6 | 86.0% | +0.15 | 10.4% |
| edge_min=1.5 | 66.4% | −0.20 | 13.4% |
| edge_min=2.0 | 53.6% | −0.28 | 16.6% |
| **edge_min=2.5（最优）** | **41.2%** | −0.20 | **22.0%** |
| edge_min=3.0 | 40.3% | −0.19 | 20.3% |

**最优仅 +0.9pt 可用率、+1.7pt 车道内，可忽略**；且越放宽越牺牲车道内（单调权衡）。

### 结论：那 420 次拒绝基本是对的，镜像路径解锁不出来

那些帧的"右边界"横向只有约 **1.6–2.4 m**，**无法被判为右边缘**（更像中线或左边界）；
按"右侧 1.75 m"镜像它必然把车放到错误一侧。所以问题不在判据窗口（虽然盲区那点仍是真缺陷、
值得为正确性修），而在于**这批数据里根本没有可用的右侧边缘证据**。

### 杠杆转移到配对率

离线链路当前：vision frame **89.9%** → `lane_frame_usable` **76.4%** → paired **26.2%** →
`choose_sensor_lane` **40.3%**。

**配对率（26.2%）才是瓶颈**：单边帧占多数，而其中能可靠判定为右边缘的极少。
要提可用率必须让**两侧边界都被检出**——这属于分割/检测轴（即目标里的"可深度学习"那条），
不是判分/门槛问题。**下一步应转到检测侧**（更好的模型或更好的两条线召回），而不是继续调镜像门控。

## 二十一、结构性发现：融合层是"哪条车道可用"的第二个 owner（2026-09-11 离线）

### 同一帧、同一份感知，两套结论

| 环节 | 城镇影子集（3 集） |
| --- | --- |
| 分割召回（GT, 各带） | **79.7–87.3%**，左右对称 |
| 严格判定 `lane_sel=sensor`（`select_lane_reference` 直接作用于配对帧） | **67.4% / 77.7%** |
| `choose_sensor_lane`（融合层，纯视觉分支） | **40.3%** |
| 线上实测 | 21–29% |

也就是说：**感知其实在 2/3 到 3/4 的帧里能提供可用的单边车道**，但这个结论被融合层
砍到 40%，再被线上（含 LiDAR 与真实导航）砍到 21–29%。

### 这是 owner 冲突，不是阈值问题

`lane/reference.py` 的契约（重构后按 `docs/fsd_realism.md` 与 `lane/__init__.py` 的说明
**应是唯一 owner**）接受单边帧：`_single_vision` = vision 源 + `confidence ≥ 0.50` + 中心 ≥3 点。
而 `choose_sensor_lane` 在它**之前**就用几何守卫（`_mirror_right_ok` /
`_mirror_near_ok` / `_vision_mirror_keeps_reference`）把同一帧挡回去，返回 None，
于是单边路径根本没机会走到 owner 面前。

**融合层实际上成了第二个、且更严格的 owner** —— 这正是那笔"单一 owner"重构要消除的结构。
上面两节的实验也说明：试图放宽这些守往往会**用错横向参考换可用率**（中心漂到 +0.16 m），
因为守卫的问题在于判据（盲区/横向量级）而非松紧。

### 未配对帧的当前归因（同一批数据）

`one_side_filtered_by_candidate_gate` **74**（主导）、`both_sides_but_no_pair` 32、
`all_markings_filtered` 25、`missing_left__mask_has_paint` 10、`missing_right__…` 1。
候选门控丢弃项：`unknown:kind` **243**（其中 151 条是真漆画）、`dashed:align` 75（70 条真漆画）。
而提取器判为 solid/dashed 的极少（1 / 2 条），绝大多数是 `unknown`——即**碎片形态**，
与前几轮的结论一致。

### 建议的方向（需决策，不宜由我单方面改动）

**让 owner 唯一**：融合层不应在 owner 之前用另一套判据否决同一帧。可选做法：

1. 融合层返回 None 但 vision 帧满足 owner 契约时，**交由 `select_lane_reference` 决定**
   （即让 `_single_vision` 真正生效），融合只负责 LiDAR 增强与防抖；
2. 或把"单边帧是否可信"的判据从融合层**移入** `lane/reference.py`，由 owner 统一实现，
   融合层只做证据合并。

两条都改变"谁说了算"，属于架构决策；且必须用**实车**验证（单边帧更多进入横向参考会直接
改变车辆行为）。**本文档只记录，不擅自实施。**

## 二十二、把单边帧交回 owner **不成立**——并纠正第二十一节的过度乐观（2026-09-11 离线）

### 实验（3 集，恢复已开，验收约束 = 中心落在本车道 |lat − (−1.75)| < 1.2）

| 变体 | 严格判定 `sensor` | 中心 lat 中位 | 中心在本车道 |
| --- | --- | --- | --- |
| 基线（仅融合） | **81.1%** | **+0.16 m** | **10.8%** |
| 交回 owner（`choose_sensor_lane` 返回 None 且满足 `_single_vision` 时用 vision 帧） | **82.2%** | **+0.16 m** | **11.0%** |

**不成立**，两个原因：

1. **回退分支几乎不触发**：`choose_sensor_lane` 有跨帧 **hold**，实际返回 None 的帧极少，
   交回 owner 只多 **+1.1pt**。第二十一节把 `chosen=40.3%`（瞬时）当成最终可用率是**读错了尺度**
   ——加上 hold 后它本就在 ~81%。
2. **更要紧的是中心位置**：两组的"可用"车道里只有 **~10%** 的中心落在本车道，
   中位横向 **+0.16 m**，也就是**落在道路中心线左侧（对向侧）**，而本车道中心应在 ≈ −1.75 m。

### 结论修正：融合守卫是横向正确性层，不是多余的 owner

第二十一节把"严格判定 67–81% vs 融合 40.3%"解读为 owner 冲突、并认为融合是第二个 owner
**是错的**。strict 模式下 owner 没有地图先验可比（side 门被跳过），**它的 `_single_vision`
本身缺少横向正确性检查**；融合层那些守卫（盲区窗口、骑线、镜像可信度）**恰恰在补这一层**。
所以不能把它们当"多余的 owner"拆掉。

**正确的表述**：杠杆不是"让更多帧被接受"，而是"**让更多帧的横向参考是对的**"。
当前单边镜像的中心之所以多数落在错误一侧，是因为被判为"右边界"的线横向只有 1.6–2.4 m
（更像中线）——两条证据在本数据里无法区分（见第十九、二十节）。

### 因此唯一可靠的杠杆仍是**双向配对率**（离线 26.2%）

两侧边界都被检出时，中心是两侧中点，横向正确性由几何保证，不依赖单边镜像的假设。
这属于**检测/分割轴**（目标里的"可深度学习"那条），不是门控或 owner 归属问题。

**本文件此前两节中"应让 owner 唯一 / 交回 owner"的建议据此撤回**；`choose_sensor_lane`
的守卫**保留不动**。

## 二十三、提升配对率：五个杠杆全部被否证；并记一个**测量方法陷阱**（2026-09-11 离线）

### 当前配对率的损失分布（673 帧，v13b，归并已开）

| 未配对类型 | 帧数 |
| --- | --- |
| **一侧完全没有候选** | **352** |
| 两侧有候选但配不上 | 99 |
| 无候选 | 46 |

对那 352 帧做 GT 核对：**缺失侧 GT 有漆画的 = 352/352（100%）**，其中
**左侧 336**、右侧 16。而被门控丢掉的 2567 条标线里，**只有 444 条与行驶方向对齐**
（≥0.65），其余 2123 条不对齐——它们不是车道边界。

### 五个杠杆，逐一受控实验后否证

| 杠杆 | 结果 |
| --- | --- |
| 放宽 `_mirror_right_ok` 的 3.0 m 近窗 | 可用率翻倍但中心横向从 −0.19 漂到 **+0.16 m**（对向侧），车道内 20.3% → 10.6% |
| 把单边帧交回 owner（含中心约束） | 仅 **+1.1pt** 可用；两组车道内都只有 ~10% |
| 放宽锯齿分类器 `marking_is_zigzag`（k=3/4/6） | 配对率**完全不变**（patch 已验证生效） |
| 把 `_collect_candidates` 的 side 读改为"可达窗口"（3.0–12 / 3.6–8 m） | 配对率**完全不变**（真实代码路径，三档一致） |
| （更早）放宽候选门控的侧向 5 m | `*:side` 丢弃项的 GT 占比为 **0%**，拒得对 |

结论：**离线可调的门控/判据杠杆已经用尽**。那 352 帧缺失侧的漆画，要么不在本车道
（别的车道/路侧，GT 里有漆但位置不对），要么与行驶方向不对齐（斑马线/停止线一类）。
**双向配对率不是靠"放宽门"能提升的**，它受限于该侧是否存在一条**本车道、沿行驶方向**的边界。

### ⚠️ 测量方法陷阱（重要，会影响以后所有对比）

影子集用"最新 3 集"选取（`hc._episodes(...)[-3:]`），而**并行会话每跑一次 benchmark
就会新增影子集**——所以**同一脚本在同一天不同时刻量到不同的基线**（本日实测：同一批
3 集的配对率在 20.2% 与 26.2% 之间漂移，纯粹因为集子换了）。

**规则：跨时间的对比必须钉住 episode 文件名**，只允许"同一脚本内、同一集子"的 A/B 相比。
此前若干轮把不同时间的数字直接对比，结论可能因此偏移。

### 下一步（轴切换）

配对率要提升，只能靠**该侧边界的检出质量/覆盖**，即数据与模型轴（目标里的"可深度学习"）。
具体候选：域平衡重训分割以提升**两侧**召回、或补采"本车道两侧都有线"的路段数据。
在拿到新证据前，**不再继续调整车道门控**。

## 二十四、域平衡对照训练：目标指标成功、但目标指标本身是错的（2026-09-11 离线）

### 训练（两臂同数据、同初始化 v13b、同 3 轮，唯一变量 = `--balance-runs`）

数据：`run_navroute_town`(525) + `run_20260830_152448`(900) + `run_bridge`(400)。
平衡臂按 run 等量采样（2160 帧/轮）；不平衡臂按原比例。

| 模型 | val mIoU | 城镇 line IoU | 山区 line IoU |
| --- | --- | --- | --- |
| v13b（基线） | — | 0.0109 | 0.0208 |
| **平衡臂** | 0.7181 | **0.0620**（5.7×） | 0.1181 |
| 不平衡臂 | 0.7104 | 0.0282 | 0.1245 |

**平衡采样在城镇上比不平衡高 2.2×，山区几乎无损** → "域平衡"假设在 IoU 上成立。

### 但任务指标显示：**line IoU 与"可配对"呈单调反相关**

895 个**钉住**的城镇帧：

| 模型 | 城镇 line IoU | 配对率 | 中心 lat 均值 | 中心在本车道 |
| --- | --- | --- | --- | --- |
| v13b | **0.0109** | **26.0%** | −0.212 | 28.8% |
| unbal（3 轮） | 0.0282 | 4.9% | −0.146 | **56.8%** |
| bal（3 轮） | 0.0620 | 6.1% | +0.306 | 20.0% |
| v8 | 0.0922 | 5.3% | −0.639 | 68.1% |

**四个点单调：IoU ↑ ⇒ 配对率 ↓。** 本次训练把城镇 IoU 从 0.0109 提到 0.0620（成功），
却把配对率从 26.0% 打到 6.1%（失败）。

### 结论（修正第二十三节的裁决）

**两套掩码指标都不能用于选型或作为训练目标**：

- 人工笔画容差召回：把山区 IoU 0.0208（近乎失明）的 v13b 评为 72.9%（见第二十三节）；
- 标注 GT line IoU：与配对率**单调反相关**，优化它等于恶化驾驶指标。

**只有任务指标（配对率 + 中心落点）算数。** 这也解释了 v13b 悖论：它在 IoU 上极差，
在驾车指标上却最好——因为标注的 "line" 类与"配对真正吃进去的细车道线"不是同一个目标。

### 下一步（深度学习轴的正确目标）

不要以 IoU 为目标重训。应当在**配对任务**上定义目标——例如以"两侧边界可配对率/
配对中心是否落在本车道"为验证指标做模型选择与早停，并考虑让掩码直接面向**细车道线**
（配对消费的形状），而不是标注的 line 类。**本文件据此撤回"以 line IoU 选型"的结论**，
第二十三节为 mountain pin v8 的理由也随之弱化（v8 的高 IoU 预示更低配对率，而山区无任务
数据可判）；该 pin 暂时保留但标注为待复核。

## 二十五、以任务指标做验证的对照训练：无重训臂能超过 v13b（2026-09-11 离线）

### 新增工具（本轮真正缺失的那一环）

`scripts/m5_seg_task_eval.py`：**按配对任务**验证/选型 checkpoint，而不是按掩码 IoU。
报告四个量：帧数、**配对率**、配对中心横向（均值/中位）、**中心落在本车道的比例**
（|lat − (−1.75)| < 1.2 m）。`--episode-names` 可钉住 episode，`--json` 落盘。
设计上把 episode 名单打印出来，就是因为影子集会随每次实车增长而漂移（见第二十三节）。

### 第三臂训练（v13b 初始化 + GT 三集 + 人工 line-only 两集 + 平衡采样，3 轮）

`--line-only-runs logs/m5_seg/manual_20260906_134128 logs/m5_seg/manual_mountain_labeled`
（非 line 像素按 255 忽略）。val mIoU 0.7149。

### 四臂在同一批钉住 episode 上的任务指标

| 模型 | 配对率 | 中心均值 | 中心在本车道 |
| --- | --- | --- | --- |
| **v13b（基线）** | **26.0%** | −0.212 | 28.8% |
| taskval（+ line-only + 平衡） | 8.2% | **+0.843** | 15.1% |
| bal（仅平衡） | 6.2% | +0.306 | 20.0% |
| unbal | 4.9% | −0.146 | **56.8%** |

**没有任何一个 3 轮微调臂在配对率上接近 v13b（26.0%）**；taskval 的中心还最差（+0.843 m，
中心在道路中心线左侧）。unbal 的"少而准"（4.9% / 56.8%）与 v8 的模式一致。

### 结论

**在当前数据与 3 轮微调的方法下，"重训以同时改善可用率与横向正确"没有成功。** v13b 的配对
优势无法用"GT 三集 + 人工 line-only + 平衡"复现——它更可能来自产出 v13b 的那套完整训练配方
（或该掩码更细/更稀疏的形态），而 GT 监督的微调会把这种形态破坏掉（第二十四节的 IoU 反相关
是同一现象的另一面）。

**可继续的方向**（都需更多数据或更长训练，且以 `m5_seg_task_eval.py` 为选型判据）：

1. 用**完整**配方重训（不是 3 轮微调），并把任务指标作为早停验证；
2. 补采"本车道两侧都有线"的路段数据；
3. 或改变监督目标本身——让掩码直接面向**细车道线**（配对消费的形状），而不是标注的 line 类。

## 二十六、"细车道线"监督目标：相对对照臂有改善，但仍远不及 v13b（2026-09-11 离线）

### 新增可复用开关

`scripts/m5_train_seg.py --thin-line-labels N`：把标线目标侵蚀 N 像素，教模型学**细**线。
`cv2.ximgproc` 不可用，形态学侵蚀是最便宜的骨架化近似；全标注集里被侵蚀的边缘记作路面(1)，
line-only 人工集里记作忽略(255)。实测 line 像素：N=0 → 1,054,802；N=1 → 621,398；N=2 → 401,261。
该参数写入 checkpoint 元数据。

### 对照（唯一变量 = 是否细化；其余与 taskval 臂完全相同）

| 模型 | 配对率 | 中心均值 | 中心在本车道 |
| --- | --- | --- | --- |
| **v13b** | **26.0%** | −0.212 | 28.8% |
| taskval（不细化） | 8.2% | +0.843 | 15.1% |
| **thin（细化=1）** | 8.8% | +0.700 | **22.8%** |

**细化确实帮助了中心落点（15.1% → 22.8%，+7.7pt）、配对率几乎不变（+0.6pt）**——监督目标的
方向被验证了一点。但**距 v13b 仍差得远**（配对率 8.8% vs 26.0%）。

### 三臂一致的结论：限制因素是"3 轮微调"这个范式，而不是监督目标

到目前为此，四个重训臂（balanced / unbal / taskval / thin）**没有一个在配对率上接近 v13b**。
它们的共同点是"从 v13b 出发、在 GT 数据上微调 3 轮"。结论：**这种微调会破坏 v13b 的配对
形态**，无论怎么调数据配比、line-only 监督或目标细化。

**因此正确的下一步是"完整配方从头重训（以任务指标做验证/早停）"，而不是继续微调**；
在拿到那样的模型之前，**v13b 继续作为城镇模型**（没有任何实验臂能替代它）。
`scripts/m5_seg_task_eval.py` 是这条路的验收工具。

## 二十七、从头重训（不微调）：方向被证实，但任务指标**非单调**（2026-09-11 离线）

配方与前面各臂一致（GT 三集 + 人工 line-only + 细化 1 + 平衡），**唯一差别是不再从 v13b 初始化**。
每轮后用 `scripts/m5_seg_task_eval.py` 在同一批钉住 episode 上评估：

| 轮数 | val mIoU | 配对率 | 中心均值 | 中心在本车道 |
| --- | --- | --- | --- | --- |
| 1 | 0.6387 | 12.0% | −0.218 | **33.6%** |
| 2 | 0.6301 | **18.3%** | +0.334 | 26.2% |
| 3 | — | **2.2%** | −0.234 | 60.0% |
| v13b（参照） | — | **26.0%** | −0.212 | 28.8% |

### 两个结论

1. **"微调范式是限制因素"被证实**：从头训练第 1 轮就有 12.0% 配对率，超过**所有**微调臂
   （balanced 6.2% / unbal 4.9% / taskval 8.2% / thin 8.8%），第 2 轮到 18.3%——即
   "从 v13b 微调会破坏配对形态"的判断成立，从头训练可以重建它。
2. **但任务指标非单调**：第 3 轮配对率崩到 2.2%（同时车道内升到 60%），与 v8/unbal 那种
   "少而准"形态一致。**而且 val mIoU 完全预测不了任务指标**（ep1 mIoU 最高 0.6387 时配对 12.0%，
   ep2 mIoU 更低却配对 18.3%）。

**因此"用任务指标做早停/选型"不是锦上添花，而是必需**：训练的 `best.pt` 按 val mIoU 选出的
checkpoint 在配对任务上可能还不如中间轮次。当前最好成绩是 **ep2 的 18.3%**，仍低于 v13b 的 26.0%。

### 下一步

按轮数扫描（每轮评估、按任务指标取最优），而不是"跑满固定轮数"——并考虑把任务指标接成
训练器里的验证回调（本轮先用外挂脚本实现）。

## 二十八、轮数扫描结论：任务指标在 ep2 见顶后单调衰减（2026-09-11 离线）

| epoch | 配对率 | 中心在本车道 | val mIoU |
| --- | --- | --- | --- |
| 1 | 12.0% | 33.6% | 0.6387 |
| **2** | **18.3%（峰值）** | 26.2% | 0.6301 |
| 3 | 2.2% | 60.0% | — |
| 4 | 5.7% | 84.3% | 0.6705 |
| 5 | 3.4% | 46.7% | 0.6719 |
| 6 | 2.9% | 34.6% | 0.6763 |
| 7 | 2.4% | 38.1% | **0.7166** |
| v13b（参照） | **26.0%** | 28.8% | — |

**val mIoU 单调上升（0.6387 → 0.7166），配对率单调下降（12.0% → 2.4%，峰值在 ep2）。**
两个目标在训练过程中**主动背离**——所以"跑满轮数"是错的做法，"按任务指标早停并取最优轮"
才是唯一合理的方式（这也再次印证第二十七节的结论）。

### 本轮全部实验的总账

| 臂 | 配对率 |
| --- | --- |
| 微调：balanced / unbal / taskval / thin | 6.2 / 4.9 / 8.2 / 8.8% |
| 从头：ep1 / **ep2（峰）** / ep3–ep7 | 12.0 / **18.3** / 2.2–5.7% |
| v13b | **26.0%** |

**本会话没有任何一个训练臂达到 v13b 的 26.0%。**

### 必须承认的混淆因素（诚实记录）

**"完整配方"并没有真正做到**：为控制时间，从头的各臂只用 3 个 run（约 1825 帧），
而仓库里有 13 个 run / 7477 帧可用，v13b 当年用的数据量很可能更大。
**所以"从头训练打不过 v13b"这一结论被数据量混淆**——真要做完整配方重训，应当用
**全部 run**，并以 `scripts/m5_seg_task_eval.py` 做逐轮验证、按任务指标取最优 checkpoint。
在那之前，**v13b 继续作为城镇模型**（有证据支撑：它仍是配对率最高的 checkpoint）。

## 二十九、两会话在"按任务指标选 checkpoint"上会合（2026-09-11 晚间）

### 并行会话已把本会话的评估器接进训练器

HEAD `f5ebd51 seg: select the training checkpoint by the pairing task, not by val mIoU` 新增：

- `--task-eval-every N`：每 N 轮调用 `scripts/m5_seg_task_eval.py`（**本会话本日新增的脚本**，

  **测量陷阱**是同一结论。

**两个会话在同一条线上会合**：本会话提出"必须按任务指标早停"并交付评估器，对方把它接成
训练器原生特性。这比各自维护外挂脚本好。

### 对方的独立结论（`0e47cfd`）

"完整配方去掉城镇数据会塌；**人工标注才是决定性成分**"——与本会话的观察一致：
本会话的 3-run 从头臂 ep1 配对 12.0%，而 12-run 完整配方 ep1 只有 **7.0%**（下方数据），
即**加入更多标线稀疏的 run 反而稀释了配对能力**（这与 README 里 `--min-line-frac`
存在的理由同源）。
