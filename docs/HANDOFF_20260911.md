## 三、本轮实现的改动：虚线边界恢复

`beamng_autopilot/vision/lanes.py`：

- `group_world_fragments`（纯逻辑，可单测）：方向一致 `|cos| ≥ 0.94`、横向共线
  `≤ 0.45 m`、纵向间隙 `≤ 8 m`、链跨度 `≤ 60 m` 的片段并成链。
- `recover_dashed_boundaries`：每条链合成**一条长边界**。
- `_mask_fragment_polylines`：把掩码连通域回投影成世界片段。
- 接线在 `Segmenter.detect_lines`，8 项单测在 `tests/test_dashed_recovery.py`。

**为什么需要它**：城镇 `line` 类不是几条连续长线——每帧 **p50 17 个连通域**、高度
中位数 **7 px**，只有 **23.8%** 能过提取器的形状门（`h≥18`、宽度、填充率）。被丢的
是**真漆画**（被丢像素 65% 落在 GT 上），但都是**亚米级碎屑**（被丢 `unknown` 标线
世界跨度 p50 0.60 m），不携带边界几何，于是本车道只剩一侧边界、永远配不成对。

**实测（3 集 654 帧，v13b）**：

| | 配成双侧本车道 | `lane_sel=sensor` |
| --- | --- | --- |
| 归并前 | 20.8% | 45.1% |
| **归并后** | **43.0%** | **55.5%** |

关键：归并出的边界**本身足够长**，是**凭自身几何合法**跨过
`LANE_PAIRED_VISION_MIN_SPAN_M = 6.0`——**跨度门槛没有被降低**。

**接线时的坑（已量）**：归并必须只吃**学习掩码**，不能吃
`white_mask = 学习 ∪ 经典CV亮线`。喂并集只有 23.9% 配对率，喂学习掩码才是 43.0%
——CV 并集里的纹理亮边不是漆画，会污染分组。经典 CV 通路保持"只保底不新增功能"。

## 四、不要重走的坑

1. **降 `LANE_PAIRED_VISION_MIN_SPAN_M`**：3.2 m 的短配对可以在"每个点都离车很近"
   的同时让中心偏离导航路线好几米（runs 42/47/52）。实测降它能把配对率"提"到 41.9%，
   但放行帧里有 18% 不在车道内——**聚合指标不能否证一条为尾部风险存在的守卫**。
   该门现已补单测（`tests/test_lane_fusion.py`）。
2. **放开标线提取守卫**：守卫是承重的（放开 `min_height` 会让"标线"从 3.0/帧涨到
   57.9/帧而配对率不动）。
3. **放开候选门控**：`*:side` 那些被丢标线的 GT 占比是 **0%**，门控正确。
4. **时序延续（last-good hold）**：掉线是**长时缺失**——16 段、185 帧、101.6 秒，
   **最长一段 35.6 秒**，1 秒以内缺口总计只有 0.3 秒。

## 九、`stale sensor` 根因确认，以及与并行进程的协同（2026-09-11 上午）

### 根因（由新加的 freshness 遥测一次定位）

用 `8303312` 新增的逐帧 `freshness` / `head_age_s` 字段跑了一轮城镇（`town_1789092137`）：

判 stale → 失败关闭停车。

**注**：此前我用录制数据"排除"过这个假设，但那次的离线模型用了 `tick_wall_ms`（~0.2 s）当帧间
间隔，而真实墙钟间隔是「暂停仿真 + 规划 + step(0.75 s)」约 0.5–0.9 s。**假设是对的，我的模型错了。**

## 十一、虚线恢复已做便宜并默认开启（2026-09-11 10:47，commit `f39d298`）

### 性能：17× 提速，且瓶颈与我预想的不同

Profile 结果：`_mask_fragment_polylines` **53.7 ms/帧**，而 `group_world_fragments`

1. `back_project` **每次调用都重建相机位姿**（3 个 cross + norm），而每帧要调 ~542 次；

## 十五、死锁真因：被拒的横向修正不该升级为整车急刹（commit `66e02cd`，已实车验证）

### 前两次归因都错了，这是第三次（有遥测证据）

| 字段（静止尾部 145 帧） | 值 |
| --- | --- |
| `painted_body_cross` | **0（全程）** ← 不是它 |
| **`plc_rejected`** | **1（全程）** ← 是它 |
| `line_lat` | **+1.838 m** |
| `plc_active` / `plc_shift` | 1 / **1.0 m** |
| `emergency` | 1（全程） |

`force_stop = bool(painted_body_cross or plc_rejected)`，而 `plc_rejected` 来自：
PLC 把路径横向修正 1.0 m → **对"修正后"的路径**重跑安全契约 → 判 minimal_risk → 拒绝
→ 升级为**整车紧急硬刹**。于是：**车因为横向修正被拒而停住，又因为停住而永远无法回到线上**
（145/145 帧的死循环）。

**未修正的路径本来是监控已经批准过的**——所以正确的语义是"跳过这个可选后处理"，
而不是把车刹死。

### 修法

- 修正被拒 → **退回未修正路径**（跳过修正）；
- `plc_rejected` 降为遥测字段，**不再参与 `force_stop`**；
- `painted_body_cross` 保留其 `force_stop`（那条是验收标准的直接几何违反）。

## 十六、尾部停车归因闭合：不是缺陷，是 strict 失败关闭 + 感知车道可用率（2026-09-11）

离线分析 `town_1789098126` 的 222 帧（**不需要车辆**）：

| 分组 | 帧数 | `lane_sel` |
| --- | --- | --- |
| `source=fsd` 且 `plan_speed=0` | 121 | **121/121 = `perception-unavailable`** |
| `source=fsd` 且 `plan_speed>0` | 29 | **29/29 = `sensor`** |
| 全区 `lane_sel=sensor` | 64 | **全部 `plan_speed>0`**（无一例外） |

即 **`plan_speed == 0` ⟺ 没有感知车道**，对应 `fsd_drive` 里那条明文契约：

```python
plan_speed = out.best_speed if out.best_speed > 0.0 else float(args.speed)
if _strict_no_lane:
    plan_speed = 0.0          # 无感知车道 → 禁止运动（strict 失败关闭）
```

**所以尾部停车是正确行为，不是缺陷**；`plan_raw` 也是 0（不是被障碍钳的——注意
`speed_profile` 的障碍项下限是 `MIN_SPEED=1.0`，且曲率项已有零长度顶点守卫，两者都不可能产出 0）。

**结论：剩余里程缺口的唯一杠杆是感知车道可用率（29%）**，不是驱动循环里的更多补丁。
唯一真实的小问题：`source=none` 的 71 帧里有 **34 帧有车道却 `no drivable path`**
（走廊/约束找不到可行路径）——这才是下一步该查的规划覆盖率问题。

### 顺带一个评测口径问题

城镇是 `strict` 运行，"无感知车道 → 停车"是规范行为，但 benchmark 的 `no_stall`
会把这些帧计为 stall。**`no_stall` 因此在 strict 场景下部分是在测量感知可用率而非
控制质量**，值得在判分口径上区分（或作为已知语义记录）。
